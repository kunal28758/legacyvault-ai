# Development Rules — LegacyVault AI

**Purpose**: How work is done on this repository — the workflow gates, the
rules for humans and AI agents, and the definition of done. This file
organizes rules that are authoritative elsewhere; it cites them rather than
restating them in full.

**Canonical sources**: constitution v2.0.1 (Principles XVIII–XXII, Governance),
[`../BRAIN.md`](../BRAIN.md) § 12 *Development Workflow* and § 17 *AI Agent
Rules*, [`../ARCHITECTURE_DECISIONS.md`](../ARCHITECTURE_DECISIONS.md),
`AGENTS.md` at the repository root.

---

## 1. Spec-Driven Development is mandatory (constitution XX)

```
Constitution → Specification → Clarification → Plan → Checklist
→ Tasks → Analysis → Implementation → Convergence
```

- Implementation of a feature MUST NOT start without an approved
  specification and plan. For the baseline these exist:
  `specs/001-baseline-product-spec/{spec,plan,tasks}.md`.
- Trivial changes may skip intermediate steps; security-sensitive or
  architecturally significant work may not.
- Architecture changes are recorded as an ADR in
  `docs/ARCHITECTURE_DECISIONS.md` **before** implementation (constitution
  VIII).
- Requirement ambiguities are resolved by adding a Clarifications entry to
  `spec.md` — never by silently changing a requirement or weakening it in a
  downstream document.

## 2. Authority order

When documents disagree: constitution → ADRs → `spec.md` → `plan.md` /
`data-model.md` / `contracts/api-contracts.md` / `research.md` → `tasks.md`
→ `docs/**` explainers. Fix the lower document.

## 3. Rules for AI agents and contributors

The full list is `docs/BRAIN.md` § 17 and constitution Governance § Agent
Compliance. The non-negotiables:

1. Read the constitution, the ADRs and `docs/BRAIN.md` before significant work.
2. Inspect the repository before changing it; never assume state. Do not
   assume `frontend/`/`backend/` or any superseded component exists.
3. Follow the specification and the task list; do not introduce Express.js,
   Prisma, S3/MinIO, Redis/BullMQ, Supabase Auth, MongoDB or custom
   authentication without a new ADR citing a concrete requirement.
4. Keep business logic in `lib/services`; every invariant-bearing write goes
   through a guarded database function (`data-model.md` § Write-Protection
   Model).
5. Never mark a task complete unless the code exists and is verified; never
   fabricate test results or deployment status (constitution XVIII).
6. Never read values from `.env.local` into documents, commits, prompts or
   logs; secrets live only in environment configuration (constitution I, XIX).
7. Preserve security boundaries: server-side authorization, RLS, signed URLs,
   reverification for sensitive operations, audit everything
   security-relevant; access tokens never in URL paths.
8. Update `docs/BRAIN.md`, `docs/PROJECT_STATUS.md` and the relevant ADR when
   architecture, rules, contracts or schema change (constitution XVIII).
9. Resolve trade-offs in the constitution's priority order: Security →
   Integrity → Correctness → Legal-Tech Safety → Maintainability →
   Accessibility → Performance → Visual Polish (constitution XXII).
10. Mark uncertainty explicitly; do not guess.

## 4. Framework rule

Next.js 16 is not the Next.js of older training data. Read the relevant guide
in `node_modules/next/dist/docs/` before writing framework-facing code, heed
deprecation notices, and use `proxy.ts` (not `middleware.ts`). `AGENTS.md`
at the root is regenerated by `next dev`; do not hand-edit it.

## 5. Task execution rules (`tasks.md`)

- Work in phase order: Phase 1 (setup) → Phase 2 (foundational; **blocks all
  user stories**) → user-story phases in dependency order → Phase 25.
- `[P]` tasks touch different files and may run in parallel; others are
  sequential within their phase.
- Stop at every phase **Checkpoint** and validate the story independently
  (quickstart scenarios, tests) before continuing.
- Task IDs are never renumbered or reused; retired IDs stay in the *Removed
  Tasks* ledger. New tasks continue the sequence (next id after T247).
- Commit after each task or logical group (constitution XIX).

## 6. Definition of done (for any task or story)

A task or story is done only when all of the following hold:

- Behaviour matches `spec.md` (FR/NFR/AC) and `contracts/api-contracts.md`;
  validated against the specification before being declared complete
  (constitution XX).
- The mandated automated tests exist and pass (constitution XVII; blocking CI
  gate T246); security-tagged suites cannot be skipped.
- No secret, stack trace, database detail or file path can reach a client or
  a log (constitution X, XVI).
- Audit rows are written for every security-relevant outcome (constitution
  XII).
- Documentation affected by the change is updated (constitution XVIII).
- Nothing implemented contradicts an ADR; if it must, an ADR revision is made
  first.

## 7. Branching, environments and release

- Branch and environment expectations are in
  [`ENVIRONMENT_MATRIX.md`](./ENVIRONMENT_MATRIX.md); the default-branch
  naming decision (`master` vs `main`) is an open owner item
  (`docs/PROJECT_STATUS.md` § 5).
- Production deployment requires the pre-production security review
  (NFR-SEC-002, T185), backups/DR in place (NFR-DR-001/002), and the
  platform prerequisites verified (T210). Security regressions block release
  (NFR-SEC-003).

## 8. What this repository is right now

Phase 0. Governance and specification are complete; a Next.js 16 scaffold
exists; **no application feature, migration, handler, test or deployment
exists** (`docs/PROJECT_STATUS.md`). Do not describe or treat anything as
implemented until the corresponding task is actually done.
