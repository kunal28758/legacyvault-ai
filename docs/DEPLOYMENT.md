## 3a. Authentication wiring (Clerk ↔ Supabase) — required for any data access

Two settings must both be in place or **every** database query fails as `anon`:

1. **Clerk issues the role claim.** Supabase maps the JWT `role` claim to the
   PostgreSQL role. A stock Clerk session token has no `role`, so the request
   arrives as `anon`, which has no grants and no policies anywhere — the
   symptom is `42501 permission denied` with a misleading hint to grant
   privileges to `anon` (never do that).

   ```bash
   npx clerk config patch --json '{"session":{"claims":{"role":"authenticated"}}}'
   npx clerk config pull        # verify: session.claims.role === "authenticated"
   ```

2. **Supabase trusts the Clerk issuer.** `supabase/config.toml`:

   ```toml
   [auth.third_party.clerk]
   enabled = true
   domain = "<your-instance>.clerk.accounts.dev"   # Clerk Frontend API host
   ```

   Restart the stack after changing this (`pnpm db:stop && pnpm db:start`).
   Staging and production register their own instance domain (§ 6, T196).

Verify both at once — this must return the caller's own row and nothing else:

```js
const token = await window.Clerk.session.getToken();
await fetch(`${SUPABASE_URL}/rest/v1/users?select=id`, {
  headers: { apikey: PUBLISHABLE_KEY, Authorization: `Bearer ${token}` },
});
```

## 4. Migration workflow (ADR-002 — SQL migrations, no ORM)

1. `pnpm db:migrate:new <name>` creates `supabase/migrations/<timestamp>_<name>.sql`.
   The baseline files are scheduled as T018 (`0001_init.sql`), T218
   (`0002_rls_and_privileges.sql`) and T019 (`0003_functions.sql`).
2. `pnpm db:reset` applies all migrations to the local stack; `pnpm db:types`
   regenerates `lib/types/database.ts`; `pnpm db:lint` runs `supabase db lint`.
3. Review checklist per migration (plan § Phase 2): every table has RLS +
   policies, every FK an index, every Class B table **no** direct write grant,
   every guarded function follows the nine mandatory rules, `EXECUTE` revoked
   from `PUBLIC`/`anon`.
4. Hosted projects receive migrations only through the CD pipeline (T238) via a
   gated `supabase db push`; never from a developer machine against production.

## 7a. AI providers and fallback (verified 2026-10-02)

Gemini stays the primary. Any other provider is called **only** when it is named
in `AI_PROVIDER_ORDER` (a key alone authorises nothing), and vault document
content — attachments, document analysis — goes **only** to providers named in
`AI_DOCUMENT_PROVIDERS` (unset: Gemini and OpenAI in development, **none in
production** — vault documents reach no AI until it names providers whose
account terms allow them, e.g. a billing-enabled Gemini project; document AI
answers "no configured AI provider is approved to read vault documents"
until then, and chat without attachments is unaffected). The chain moves on only
for an outage, a timeout or a spent quota; a refusal, an invalid request,
rejected credentials or an answer that fails validation is reported as it is.
A model that cannot read a request's file (an image to a text-only model, a
HEIC photo to a PNG/JPEG-only model, a PDF to anything but Gemini/OpenAI) is
skipped rather than sent it. Capabilities are declared per verified model in
`lib/ai/providers/openai-compatible.ts`; an unlisted model is text-only.

**Paid usage.** OpenRouter models must end in `:free` unless
`OPENROUTER_ALLOW_PAID_MODELS=true`. Whether a Groq, Cerebras, Hugging Face or
OpenAI call is billed depends on that account's plan, which the application
cannot see — keep those accounts on their free plans (or without purchased
credit) if fallback must never cost money, and name them in
`AI_PROVIDER_ORDER` only deliberately.

**Recommended configuration** (production): a billing-enabled `GEMINI_API_KEY`
(the free tier must not receive vault documents under Google's own terms), then
free text fallbacks that do not retain data:

```
AI_PROVIDER_ORDER=gemini,groq,cerebras
AI_DOCUMENT_PROVIDERS=gemini
GROQ_API_KEY=…    # free plan; enable Zero Data Retention in Groq's Data Controls
CEREBRAS_API_KEY=…
```

Add `openrouter` to the order for a vision-capable free fallback only after
reviewing which provider serves the chosen `:free` model and its data policy;
add it to `AI_DOCUMENT_PROVIDERS` only if that policy is acceptable for private
documents.

**Deploy:** set the variables above in Vercel (server scope), redeploy, then
sign in and check `/ai` — the badge lists the primary and the fallback chain.
Server logs record each attempt as `AI provider call` / `AI provider call
failed` with provider, model, duration, outcome and `upstream`
(status/reason/quota) — never content.
**Rollback:** remove `AI_PROVIDER_ORDER` (the chain reverts to Gemini/OpenAI
only) and `AI_DOCUMENT_PROVIDERS`; no data or migration depends on them.

## 7c. Scheduler (pg_cron + pg_net, migration 0010)

Every time-based behaviour — the job runner, the hourly Dead Man's Switch scan,
the daily housekeeping — is driven by calls to the protected
`/api/internal/cron/*` routes. Migration 0010 schedules those calls from the
database:

| pg_cron job | Schedule (UTC) | Route |
|---|---|---|
| `legacyvault-run-jobs` | `*/10 * * * *` | `/api/internal/cron/run-jobs` |
| `legacyvault-dms-scan` | `7,37 * * * *` | `/api/internal/cron/dms-scan` (one scan per hour: the key is the hour) |
| `legacyvault-housekeeping` | `17 3 * * *` | `/api/internal/cron/housekeeping` |

Each job runs `public.lv_trigger_scheduler(path)`, which accepts only those
three paths, reads the base URL and the bearer from **Supabase Vault**
(`legacyvault_app_url`, `legacyvault_cron_secret`) at call time, and does
nothing when either is missing. Neither value is in the repository. The
function is executable only by its owner (no API role, not even
`service_role`). The routes are unchanged: constant-time `CRON_SECRET` check,
`claim_jobs()` with `SKIP LOCKED`, idempotent jobs — so a second caller (the
GitHub workflow, a manual `curl`) can never double-process anything.

**One-time setup per environment** (SQL editor, or
`supabase db query --linked` — paste the values; do not echo them in a shell
that logs):

```sql
select vault.create_secret('https://<production host>', 'legacyvault_app_url');
select vault.create_secret('<the CRON_SECRET set in Vercel>', 'legacyvault_cron_secret');
```

**Rotating `CRON_SECRET`:** set the new value in Vercel and redeploy, then
`select vault.update_secret(id, '<new value>') from vault.secrets where name = 'legacyvault_cron_secret';`
and update the GitHub repository secret.

**Verifying:** `select jobname, schedule, active from cron.job;` — then, after
a tick, `select status, start_time from cron.job_run_details order by start_time desc limit 10;`
and `select status_code, error_msg, created from net._http_response order by created desc limit 10;`
(responses are kept about six hours; the request headers, and so the bearer,
are not stored there). The operator health view (`/api/v1/health` with the
bearer) reports `jobs.lastRunAgeSeconds` and `dmsScan.lastSuccessAgeSeconds`;
both should stay under an hour.

### Browser checks (staging only, synthetic accounts)

Use two accounts, e.g. `<you>+lv-staging-1@<domain>` (no second factor) and
