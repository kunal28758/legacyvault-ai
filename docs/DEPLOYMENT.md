## 2. Environment variables

The schema of record is `lib/config/env.schema.ts` (task T007); `.env.example`
lists every variable with placeholders. Validate a local file with
`pnpm env:check` (prints variable names and messages only — never values).

| Variable | Scope | Where it lives | Notes |
|---|---|---|---|
| `APP_URL` | server | Vercel env / `.env.local` | absolute origin used in emails and links |
| `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `CLERK_SECRET_KEY`, `CLERK_WEBHOOK_SIGNING_SECRET` | public / server / server | Clerk dashboard → Vercel env | proxy and `<ClerkProvider>` activate when the two keys exist |
| `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | public | Supabase dashboard / `supabase status` | publishable key has **no** data access by policy (ADR-004) |
| `SUPABASE_URL`, `SUPABASE_SECRET_KEY` | server | Supabase dashboard / `supabase status` | secret key = service role; server code only (T028) |
| `ENCRYPTION_KEY` (`<keyId>:<base64 32 B>`), `ENCRYPTION_KEY_PREVIOUS` (rotation only) | server | generated by the owner, stored in Vercel env | never alongside the data (constitution IV); rotation runbook T240 |
| `ACCESS_COOKIE_KEY` (base64 32 B) | server | generated by the owner | dedicated to the access cookie (ADR-014) |
| `OPENAI_API_KEY`, `GEMINI_API_KEY`, `AI_DEFAULT_PROVIDER` | server | provider consoles → Vercel env | never `NEXT_PUBLIC_` (FR-L009, FR-R002) |
| `RESEND_API_KEY`, `EMAIL_FROM`, `EMAIL_WEBHOOK_SECRET` | server | Resend dashboard | ADR-009 |
| `SENTRY_DSN`, `NEXT_PUBLIC_SENTRY_DSN` | server / public | Sentry project | server DSN required in production |
| `CRON_SECRET` (≥ 32 chars) | server | Vercel env (Vercel Cron sends it automatically) | ADR-006 |
| `MALWARE_SCANNER_PROVIDER`, `CLAMAV_HOST`, `CLAMAV_PORT`, `CLAMAV_TLS` | server | Vercel env | ADR-015 |
| `ADMIN_EMAIL` | server | Vercel env | first Super Admin (T033) |

Secrets are managed only through Vercel environment variables (and `.env.local`
locally). `.env*` is git-ignored except `.env.example`; the env schema rejects
any secret-like name carrying the `NEXT_PUBLIC_` prefix.

## 3. Local development setup

```bash
pnpm install
cp .env.example .env.local          # fill placeholders; run `pnpm env:check`
pnpm dev                            # http://localhost:3000 — landing page works without Clerk

# Database (requires Docker Desktop running) — Phase 2 onwards
pnpm db:start                       # supabase start → prints URL, publishable/secret keys, JWT secret
pnpm db:reset                       # apply supabase/migrations + seed (T018/T218/T019 will add them)
pnpm db:types                       # supabase gen types typescript --local > lib/types/database.ts

# Quality gates
pnpm lint · pnpm typecheck · pnpm test · pnpm test:integration · pnpm test:e2e (once: pnpm test:e2e:install)
```

`pnpm lint` is the ESLint verification command: `eslint . --max-warnings=0
--no-error-on-unmatched-pattern` — warnings fail the gate, and explicit targets
that contain no lintable files (the T001 skeleton directories `hooks/`,
`stores/`, CSS-only `styles/`) do not abort the run. Extra paths can be
appended: `pnpm lint app components lib hooks stores styles`.

Behaviour without Clerk keys (documented, deliberate): the proxy fails closed —
public routes render with the CSP nonce, every protected route answers
`503 AUTH_NOT_CONFIGURED`; `<ClerkProvider>` is mounted only when the
publishable key exists. Set the two Clerk keys to enable sign-in (Phase 3).

## 4. Migration workflow (ADR-002 — SQL migrations, no ORM)

1. `pnpm db:migrate:new <name>` creates `supabase/migrations/<timestamp>_<name>.sql`.
   The baseline files are scheduled as T018 (`0001_init.sql`), T218
   (`0002_rls_and_privileges.sql`) and T019 (`0003_functions.sql`).
2. `pnpm db:reset` applies all migrations to the local stack; `pnpm db:types`
   regenerates `lib/types/database.ts`; `pnpm db:lint` runs `supabase db lint`.
3. Review checklist per migration (plan § Phase 2): every table has RLS +
   policies, every FK an index, every Class B table **no** direct write grant,
   every guarded function follows the nine mandatory rules, `EXECUTE` revoked
   from `PUBLIC`/`anon`.
4. Hosted projects receive migrations only through the CD pipeline (T238) via a
   gated `supabase db push`; never from a developer machine against production.
